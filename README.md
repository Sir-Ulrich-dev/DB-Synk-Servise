# DB-Synk-Servise

Сервис двусторонней инкрементальной синхронизации данных между Oracle и PostgreSQL с веб-панелью администратора.

1. Цель проекта

DB Sync Service — приложение для настройки, запуска и мониторинга синхронизации данных между двумя реляционными базами данных: Oracle и PostgreSQL.

Проект разрабатывается поэтапно с использованием AI-агента Claude Code. Основной акцент — надёжность синхронизации, тестируемость, понятная архитектура и простота сопровождения.

2. Основные возможности

Планируемые возможности системы:

Настройка подключений к Oracle и PostgreSQL.
Проверка доступности баз данных.
Настройка задач синхронизации.
Двусторонняя инкрементальная синхронизация данных.
Настройка правил сопоставления таблиц и столбцов.
Обнаружение вставок и обновлений.
Обработка удалений и конфликтов изменений.
Запуск задач вручную и по расписанию.
Просмотр статусов и истории выполнения.
Просмотр ошибок и результатов синхронизации.
Автоматическое тестирование бизнес-логики.

Функциональность будет добавляться постепенно. Наличие пункта в списке не означает, что он уже реализован.

4. Архитектура

На начальном этапе используется модульный монолит. Микросервисы не требуются.

Предполагаемое разделение приложения:

ui — страницы и компоненты Vaadin.
application — сценарии использования и координация операций.
domain — бизнес-модели, правила синхронизации и разрешения конфликтов.
sync — механизм обнаружения, передачи и применения изменений.
infrastructure — JDBC-доступ, конфигурация подключений и внешние интеграции.
scheduler — запуск задач по расписанию.
observability — статусы выполнения, журналирование и диагностика.

Это предварительная структура. Детальное разбиение пакетов следует уточнить при проектировании, избегая ненужного усложнения.

5. Принципы синхронизации

Синхронизация должна проектироваться с учётом следующих требований:

Поддержка изменений в обеих базах данных.
Инкрементальная обработка изменений без полного копирования данных при каждом запуске.
Идемпотентная обработка, позволяющая безопасно повторять операции.
Явная стратегия разрешения конфликтов.
Учёт удалений, чтобы удалённые записи не восстанавливались автоматически без предусмотренного правила.
Обработка ошибок и возможность безопасного повторного запуска.
Пакетная обработка записей для ограничения потребления ресурсов.
Диагностика частично выполненных операций и возможность восстановления.

Способ обнаружения изменений пока не зафиксирован. Возможные подходы включают метки времени изменения, журналы изменений, триггеры или механизмы CDC. Выбор должен учитывать ограничения обеих СУБД и доступную инфраструктуру.

Нельзя считать updated_at универсальным решением: оно не гарантирует обнаружение удалений и может не отражать все необходимые изменения.

Правила разрешения конфликтов должны быть определены до реализации полноценной двусторонней синхронизации.

6. Требования к безопасности
Не хранить пароли и другие секреты в исходном коде или Git.
Использовать переменные окружения или подходящее хранилище секретов.
Не выводить пароли и строки подключения с секретами в логи.
Ограничить доступ к административным операциям.
Использовать принцип минимально необходимых прав для учётных записей баз данных.
Не выполнять изменения структуры пользовательских таблиц без явного согласования.
Не использовать реальные производственные данные в тестах без соответствующего разрешения и защиты.

8. Локальная разработка

Предполагаемая среда разработки — локальная машина с JDK 21, Git, Docker и Docker Compose.

PostgreSQL можно запускать локально в контейнере. Доступ к Oracle пока не определён и должен быть уточнён отдельно.

На первом этапе приложение должно собираться и тестироваться без обязательного подключения к Oracle. Настройки подключений необходимо отделить от бизнес-логики.

Инструкции по запуску, переменные окружения и пример конфигурации без секретов будут добавлены после создания каркаса приложения.

12. Настройка AI-агента

Режим работы по умолчанию: acceptEdits — агент предлагает и применяет изменения автоматически, но требует явного подтверждения для деструктивных операций (git push, удаление файлов).

Права доступа (`.claude/settings.json`):
- allow: тесты (`./mvnw test`), линтер (`./mvnw checkstyle:check`), коммит (`git commit`), сборка (`./mvnw clean install`).
- ask (требует подтверждения человека): `git push` — отправка изменений на удалённый репозиторий.
- deny: чтение `.env` (`cat .env`), удаление файлов (`rm -rf`), установка небезопасных зависимостей.

Личные настройки разработчика хранятся в `.claude/settings.local.json` и добавлены в `.gitignore` — в репозиторий не попадают.

Автоматические проверки (`.agents/hooks.json`):
- `lint-after-edit`: после редактирования Java-файла автоматически запускается `./mvnw checkstyle:check`.
- `protect-sensitive-files`: блокирует попытки агента записать изменения в `.env`, `.git/*`, `*lock.json`.

Переиспользуемые навыки (`.agents/skills/`):
- `write-tests` — агент вызывает самостоятельно при изменении бизнес-логики или сервисов.
- `review-pr` — запускается вручную командой "проведи review-pr" перед слиянием ветки в main.

Правила для части кода (`.agents/rules/`):
- `repository-rules.md` — специфичные ограничения для слоя `com.dbsync.repository`: параметризованные запросы, запрет DDL, батчинг.

Память между сессиями (`docs/`):
- `docs/plan.md` — план разработки по этапам с чекбоксами (обновляется по ходу работы).
- `docs/memory.md` — журнал: что сделано, ключевые решения, следующие шаги, ловушки.

Интеграция MCP и проверка UI (`e2e/`, `.agents/mcp_config.json`, `.mcp.json`):
- **MCP-сервер:** настроен Chrome DevTools MCP (`chrome-devtools-mcp`) для управления браузером, инспекции DOM и снятия метрик.
- **E2E-тестирование UI:** тесты веб-интерфейса ([`docs/calculator.html`](docs/calculator.html)) реализованы в [`e2e/tests/calculator.e2e.test.js`](e2e/tests/calculator.e2e.test.js).
- **Сценарии и проверки:** автоматизированный прогон цепочки вычислений, захват реального скриншота ([`e2e/test-results/calculator-e2e-screenshot.png`](e2e/test-results/calculator-e2e-screenshot.png)) и валидация 0 ошибок консоли браузера.
- **Запуск:** `npm --prefix e2e test` (10/10 зелёных проверок).
